# Подключение Didox и Smartup без истории переписки

## Состояние поставки

Локальный обработчик «0.1.1» готов к запуску и проверке по [RUNBOOK.txt](RUNBOOK.txt).
Окно настройки сохраняет ссылки на сайты, «ИНН организации» и «адрес погрузки».
Код авторизации, запросов к системам, создания и подписания ТТН нужно реализовать.
Внешние аккаунты при разработке этой версии не подключались.

Полные бизнес-правила и карта полей — [HANDOFF.md](HANDOFF.md).
Исходные скриншоты и переписка для понимания алгоритма не требуются.

## Что запросить одним списком у владельца аккаунтов

| Что нужно | Для чего и как проверить |
| --- | --- |
| «Ссылка Smartup» и доступ пользователя | Открыть нужную организацию и «Продажа → Архив заказов» |
| Параметры доступа Smartup API, если выбран API | Уточнить «project_code», «filial_id» и при необходимости «filial_code» у администратора; проверить доступность архивных заказов |
| Аккаунт Didox, «ИНН организации» и права | Прочитать нужную СФ, создать ТТН, затем подписать/отправить от правильной компании |
| Партнёрский доступ Didox, если выбран API | Получить партнёрский токен по официальной документации, проверить среду и пользовательский токен |
| ЭЦП и рабочий клиент E-IMZO | Проверить ключ и полномочия на компьютере подписанта; владельцу нужно проверить доступность подписания в аккаунте |
| Одна реальная пара «СФ ↔ заказ Smartup» | Сверить клиента, дату, сумму с НДС, водителя и автомобиль |
| Запись единого «адреса погрузки» из Didox | Получить не только строку адреса, но и нужную запись/идентификатор справочника |
| Справочник водителей | «Госномер автомобиля», «модель», «ФИО водителя», «ПИНФЛ»; передать разработчику отдельно |
| Расстояния по районам и сведения о весе | Согласовать приблизительные километры; проверить источник и единицы брутто/нетто |

Эти данные пока не предоставлены. Учётные данные, ключи ЭЦП и реальные
ПИНФЛ не публиковать в репозитории: владелец передаёт их разработчику отдельно.
Технический способ подключения и хранения сессий выбирает разработчик.
Для частных справочников можно использовать «local-data/», исключённую из Git;
автоматического чтения этой папки в текущей версии нет.

## Официальные отправные точки

Ссылки проверены «20.10.2026». Доступность конкретных методов и полей в
аккаунтах заказчика ещё не проверялась.

### Didox

[Авторизация](https://api-docs.didox.uz/ru/home): для API нужны партнёрский
доступ и токен пользователя; заголовки «Partner-Authorization» и «user-key».
В документации указаны среды «https://testapi3.didox.uz/» и
«https://api-partners.didox.uz/». Вход в браузер сам по себе этих параметров
программе не передаёт. Получение доступа и полномочия компании проверить до
реализации записи документов.

[Работа с документами](https://api-docs.didox.uz/ru/integrators-documents):
чтение — «GET /v1/documents/{id}», список — «GET /v2/documents»,
черновик ТТН — «POST /v1/documents/041/create/ru»,
исходящее подписание/отправка — «POST /v1/documents/{id}/sign».
Для «ID СФ» требуется идентификатор документа Didox длиной «32» символа,
а не номер СФ или внутреннее поле «facturaid». Подписание включает ЭЦП и
timestamp; перед ним проверить требование принятой оферты в аккаунте.
Сохранение черновика и подписание — разные действия.

[JSON документов](https://api-docs.didox.uz/ru/integrators-property-documents)
задаёт структуру ТТН; её обязательные поля сопоставить с картой из
[HANDOFF.md](HANDOFF.md). Сначала подтвердить поддерживаемую связь новой
ТТН с существующей СФ: механизм привязки ещё не проверен на реальном документе.

### Smartup

[Официальная документация](https://api.greenwhite.uz/) описывает Basic Auth
по HTTPS и заголовки «project_code», «filial_id». Экспорт заказов:
«POST https://smartup.online/b/trade/txs/tdeal/order$export»;
в документации для архивных заказов указан статус «A». Это пример API-адреса
поставщика; рабочий сервер и организацию нужно подтвердить у администратора.

Проверить ограничения аккаунта по глубине истории и числу запросов: документация
содержит лимиты, включая окно «7» дней, и объект «limits». Наличие нужной старой
СФ не гарантирует доступность соответствующего заказа через API. Для этого
сначала испытать реальную дату, особенно если заказ старше недели.

Наличие «ФИО водителя», госномера, суммы с НДС и «ИНН клиента» в конкретном
ответе API не подтверждено. Проверить сами поля и необходимые справочники;
не угадывать названия по колонкам интерфейса. Если API не даёт нужных данных,
согласовать доступный способ чтения, включая интерфейс «Архива заказов».

## Порядок реализации

1. Пройти локальную проверку на [examples/sf_demo.csv](examples/sf_demo.csv).
   Без этого доступы не нужны; ожидаемые показатели есть в
   [examples/README.md](examples/README.md).
2. Выбрать API или браузерный путь для каждой системы после проверки доступов.
   Уточнить реальные API-адреса и идентификаторы организации. Текущие
   «didox_url» и «smartup_url» используются только кнопками открытия сайтов.
3. Реализовать чтение СФ и заказа без изменений удалённых документов.
   Проверить «ИНН», дату и сумму с НДС. Получить весь набор полей из
   «HANDOFF.md»; при пропусках и неоднозначности показывать строку человеку.
4. Подготовить данные ТТН для просмотра: товары целиком, стоимость без НДС,
   правильные адреса и водитель, нулевая стоимость доставки. Использовать
   десятичную арифметику и исходные суммы, не числа с плавающей точкой.
5. Добавить постоянный журнал результатов, например SQLite из стандартной
   библиотеки Python. Ключ: «организация + ID СФ»; хранить «ID ТТН», состояние,
   время и результат. При повторе или тайм-ауте сначала сверить удалённый
   результат и связь с СФ, затем решать о повторном создании.
6. Реализовать создание черновиков и отчёт со ссылками, выбор для проверки,
   исправления и отдельное действие «Подписать и отправить» с ЭЦП.
   Флаги подключения и кнопку создания включать по результату проверки
   соединения и прав, а не по факту заполнения ссылки.
7. Пройти [приёмку интеграции](HANDOFF.md#приёмка-интеграции), включая повторный
   запуск, несколько совпадений, отсутствие данных и частичный сбой пакета.

## Где менять программу

| Место | Текущая роль и нужное расширение |
| --- | --- |
| «invoice_processor.py» | Оставить локальную проверку входного списка; использовать «normalized» для поиска |
| «settings.py», «config.example.json» | Сейчас разрешены только «schema_version», «didox_url», «smartup_url», «company_tin», «loading_address»; новые параметры нужно явно добавить в схему и проверки |
| Новые модули подключения | Разделить получение данных Didox, Smartup, построение ТТН и журнал; в текущем проекте таких модулей нет |
| «app.py» | Добавить серверные операции и реальные статусы; действующие маршруты перечислены в «HANDOFF.md» |
| «web/app.js», «web/index.html» | Добавить просмотр ТТН, результаты каждой строки, исправления и отдельный выбор на подпись |
| CSP в «app.py» | Сейчас соединения браузера ограничены своим сервером; путь взаимодействия с локальным E-IMZO продумать отдельно |
| «tools/package_release.py» | Добавлять новые поставляемые файлы в явный список «FILES» |

Токены и пароли не добавлять в существующие поля ссылок: их схема специально
не принимает такие значения. «ready» означает только правильный формат строки;
«ttn_created=false» и флаги подключения сейчас намеренно постоянны.

После реализации обновить документы, версию, сборку и тесты. Пока можно
начинать разработку по этому репозиторию, но запустить реальные ТТН одним
заполнением URL невозможно.
