# Передача разработчику: Didox → Smartup → ТТН

## Что передано

Версия «0.2.0» запускается локально без сторонних библиотек Python. Работают
импорт XLSX/CSV, редактирование, проверка реквизитов, поиск повторов/конфликтов,
выгрузка отчёта CSV и выбранного списка XLSX. В окне можно сохранить ссылки
на системы, «ИНН организации» и один «адрес погрузки».

Реализованы клиенты API Didox/Smartup, вход, подбор заказа, подготовка JSON,
создание выбранных черновиков, PDF, журнал и отдельная подпись E-IMZO.
Проверено на локальном имитаторе, включая одну и три СФ, частичный отказ и
неопределённый результат. Проверка на реальных аккаунтах ещё не проводилась.
Официальную связь новой ТТН с существующей СФ нужно подтвердить в Didox;
текущая программа хранит пару в локальном журнале, исходную СФ не меняет.

Запуск и проверка установки описаны в «RUNBOOK.txt». Для работы со списком
доступы к Didox и Smartup не нужны. Для интеграции их предоставляет заказчик.
Технический порядок подключения, официальные ссылки и перечень доступов:
[INTEGRATION.md](INTEGRATION.md). Для проверки локальной части есть
[демонстрационный список](examples/sf_demo.csv) и [ожидаемый результат](examples/README.md).

## Последовательность обработки

1. Пользователь загружает список. Обрабатываются только перечисленные СФ.
   Вместо файла может получить список из Didox по датам/ИНН покупателя/статусу
   и явно отметить строки. Пустой Excel-шаблон и заполненный тестовый пример
   скачиваются из интерфейса; выбранные реальные СФ можно выгрузить в XLSX.
   «ID СФ» — точный ключ; без него нужны вместе «Номер СФ», «Дата СФ»,
   «ИНН клиента». Не выбирать первую найденную СФ при неоднозначности.
2. Получить СФ из Didox, проверить принадлежность выбранной организации
   и доступность операции. Направление/статус не являются глобальным отбором
   всех документов. При указанных дополнительных реквизитах сверить их с СФ.
3. В Smartup найти заказ: «Продажа → Архив заказов», по «ИНН клиента»,
   «дате СФ» и «Стоимости поставки с учётом НДС» СФ. По материалам колонка
   даты называется «Дата доставки». Соответствие полей проверить на реальной
   паре документов. Без совпадения или при нескольких совпадениях — проверка
   человеком; не расширять диапазон дат и не выбирать первый заказ молча.
4. Подготовить одну ТТН на одну СФ со всеми товарными позициями и количествами.
5. Создать черновик, записать идентификатор/ссылку и результат по каждой СФ.
   До повторного запуска проверить уже созданные ТТН, чтобы не создать дубль.
6. Показать черновики для проверки и исправлений. Затем пользователь выбирает
   готовые ТТН и действие «Подписать и отправить» с ЭЦП.

## Карта полей

| Поле ТТН | Источник или правило |
| --- | --- |
| «Номер», «Дата», «Договор» | Соответствующая СФ |
| «Тип ТТН» | «Стандартный», в примере перевозка «От продавца до покупателя» |
| «Грузоотправитель», «Экспедитор», «Грузоперевозчик» | Одна организация; включить соответствующие признаки совмещения |
| «ФИО водителя» | Smartup: колонка «Экспедитор» найденного заказа |
| «Госномер», «Модель авто» | Код авто из найденного заказа Smartup → проверенный справочник машин; недостающее заполнить |
| «ПИНФЛ водителя» | Отдельный справочник заказчика по номеру машины; сверить ФИО |
| «Ответственное лицо, доставляющее груз» | Тот же водитель |
| «Адрес погрузки» | Один постоянный адрес из «Моих адресов» Didox; выбрать запись при подключении |
| «Адрес доставки» | Из СФ: область/город, район, улица, дом; сохранить дополнительные элементы |
| «Наименование», «ИКПУ», «Единицы», «Количество», «Цена» | Все товарные строки соответствующей СФ |
| «Сумма груза без НДС» | «Стоимость поставки» СФ без НДС; сохранить точные исходные суммы |
| «Масса брутто», «Масса нетто» | Сначала проверить СФ; при отсутствии связанную реализацию Smartup; отсутствие показать человеку |
| «Расстояние» | Приблизительное, редактируемый справочник по адресу погрузки и району доставки |
| «Стоимость доставки за 1 км», «Стоимость доставки» | «0» |

Сумма для поиска заказа — **с НДС**. Стоимость груза в ТТН — **без НДС**.
Не вычислять сумму заново из округлённой показанной цены, если исходная СФ
содержит более точную сумму. Не заменять отсутствующие веса нулями.
Демонстрационные водители и машины из разных скриншотов не задают константы.

## Что получить и проверить у заказчика

- «Ссылка Smartup», организация и доступ к нужным данным; способ авторизации
  выбрать после изучения доступного API или интерфейса конкретного аккаунта.
- Доступ Didox и ЭЦП; возможность создать ТТН и официально связать её
  с уже существующей СФ. Механизм этой связи ещё не проверен.
- Конкретная запись единого «адреса погрузки» из справочника Didox.
- Справочник «номер машины → ПИНФЛ водителя»; в поставке персональных данных нет.
  Можно получить из Smartup ФИО/коды машин за выбранные дни и дополнить список
  в окне либо CSV. ПИНФЛ и модель публичный экспорт заказов не описывает.
- Реальная пара «СФ ↔ заказ Smartup» для проверки даты и суммы с НДС.
- Доступность веса и единиц; значения расстояний по районам ещё не заданы.

Здесь собраны все известные недостающие данные; читать исходную
переписку для восстановления правил не требуется. Адреса, доступы и частные
справочники всё равно должен предоставить владелец аккаунтов.

## Точки расширения кода

«invoice_processor.py» выполняет только локальные операции и возвращает
нормализованные строки. «status=ready» означает правильный формат реквизитов,
а не существование документа в Didox. Его «ttn_created» относится только
к локальному списку; результаты создания хранятся отдельно в журнале ТТН.

«settings.py» читает параметры; файл по умолчанию — «config.local.json».
В нём нет паролей и токенов. Доступы вводятся в окне и хранятся в памяти.
«connectors.py» содержит API-клиенты, «workflow.py» — проверки, журнал и
операции подготовки/создания/подписи; «web/integration.js» — интерфейс.

Текущие маршруты «app.py»:

| Метод и адрес | Назначение |
| --- | --- |
| «GET /api/status» | Версия и фактические флаги доступности систем/создания |
| «GET /api/settings», «POST /api/settings» | Чтение/сохранение параметров; POST: JSON с объектом «settings» |
| «GET /api/template» | Пустой шаблон Excel |
| «POST /api/import?filename=...» | Импорт, тело — байты файла; необязательный «sheet» выбирает лист |
| «POST /api/validate» | Проверка JSON-объекта с массивом «rows» |
| «POST /api/export» | Выгрузка по «kind=report» или «kind=list», «rows», «selected_ids» |

Операции ТТН доступны в «/api/integration/»: «connect», «disconnect»,
«prepare», «edit», «create», «jobs», «report», «pdf», «save-references»,
«reconcile», «confirm-absent», «catalogs», «sign-data», «sign», «auth-timestamp».
Формат вызовов показан в «web/integration.js», интеграционные сценарии —
в «tests/test_integration.py». Первая проверка описана в «INTEGRATION.md».

Сервер оставлять локальным: авторизации пользователей самого приложения нет.
Для совместного сервера потребуется отдельно проектировать вход и доступы.
Статусы подключения и кнопку создания включать после успешной проверки
интеграции, отдельно от факта сохранения URL.

## Приёмка интеграции

Сначала одна согласованная СФ: найти точный заказ, сверить все перечисленные
поля, создать и открыть черновик, подтвердить связь с СФ и суммы. Повторный
запуск не создаёт второй черновик. Затем проверить несколько СФ, отсутствующий
заказ, несколько совпадений, неполные реквизиты и продолжение после ошибки.
После проверки черновиков испытать «Подписать и отправить» на выбранных
заказчиком документах с его ЭЦП. Исходный Excel не изменять.
